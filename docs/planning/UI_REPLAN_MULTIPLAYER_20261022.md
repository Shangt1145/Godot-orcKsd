## 需要优先修正的具体问题

1. **技术面板仍是主要界面。** RoomScreen 的标题、实例面板、开局检查包含“拉起服务器实例”、座位 0/1、卡池 policy、指纹以及尚未开放 Agent。玩家主体应是“我／对手、邀请好友、添加电脑对手、开始对战”；技术信息放可展开的连接详情，未开放功能移出主路径。
2. **卡组回退改变玩家预期。** OpenAsync／JoinAsync 在 TryActiveDeck 失败时自动使用 LobbyDeck。下一步应先显示具体卡组和后端验证结果，无效时提供“更换卡组”，示例卡组需明确选择。客户端只做呈现与预检查，合法性最终由后端判定。
3. **对手卡组展示不可信。** ApplySnapshot 给双方座位都传入本机 `_deck` 生成的标签。只显示本端真实卡组；对手未通过协议公开的数据展示“对手已加入／等待”，不要把本机卡组伪装成对手信息。
4. **发现列表以地址为标题。** Setup 的房间行当前突出 Host:Port 与座位数。优先使用发现协议已有的房间显示名，辅以人数和可加入状态，地址留作次要信息；未提供的数据不能凭空补齐。
5. **布局密度与职责混杂。** 创建、加入、网络详情、座位操作同时堆在房间左栏。创建与加入在准备页选择；房间页专注双方与开局，手动地址加入作为补充入口。

## 页面与状态方案

作战准备：当前卡组（名称、封面、张数、可用状态、更换）→ 单人练习／创建房间／加入房间。发现列表支持直接加入与手动输入地址。

作战房间：我方卡组与连接状态、对手位置、邀请好友／电脑对手、主操作“开始对战”。客人显示“等待房主开始”；缺少条件时给出原因。

状态至少覆盖：准备中、发现为空、正在加入、加入失败、等待对手、可以开始、正在开局、连接中断、正在重连、恢复成功、离开。异步结果必须核对当前房间／页面生命周期，防止返回后旧回调重新改写界面。取消与离开不能依靠隐藏按钮冒充释放资源。

保留现有 `RemoteMatchFeed`、命令映射、服务器生命周期与重连单飞守卫；先梳理事件与控件边界，再逐块替换布局。UI 不新增判伤、胜负、选靶或卡组规则。

## 实施顺序和验收

1. **卡组与信息真实性**：先解决无效卡组回退、双方卡组标签及错误原因，补充行为测试。
2. **作战准备页**：统一单机／建房／加入层级，房间列表和手动输入各有明确入口。
3. **房间页**：以两位参与者和开局动作为中心，折叠连接详情，替换工程术语。
4. **状态反馈**：空列表、满房、加入失败、退出、重连、客人等待；保留延迟信息但降低视觉权重。
5. **工坊与资产一致性复核**：沿用全部卡包统一编辑入口及草稿恢复；旧兼容卡不能仅因外观统一便宣称可进入原生联机卡池。不在此轮强行迁移旧资产。

每阶段检查 1600×900 和窄窗口实际画面、键盘焦点和减弱动效。验证首页→准备→建房／加入→开局的真实点击链，覆盖双方不同卡组、无效卡组、满房、房主／客人返回、断线后恢复和选靶中断线。

复用 `tools/run.ps1` 的 VerifyRoomJoin、VerifyRoomRemote、VerifyRoomReconnect、VerifyRoomDiscovery、VerifyRoomSegments、VerifyRoomPing、VerifyTarget、VerifyCombat、VerifyDeck 探针；工坊全入口和单机演出也需回归。已有 ROOM_JOIN_VERIFY_OK／ROOM_REMOTE_VERIFY_OK 仅作为历史证据，不替代重构后的运行结果。

本轮完成检查与方案，不改产品界面、不启动新服务器、不推送或重新发行。下一轮从第 1 项实施，避免一次换壳后才发现数据展示或路由未适配。
