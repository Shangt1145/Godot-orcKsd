## 目标与当前现场

OrC-KSD 全称 Origin Compiler-KardsSimulatorDrive，招牌是原语组合器、原语编辑器和自动解析器。目标：傻瓜式制作复杂 DIY，并用于对战，同时保留高扩展性。

## 引擎开发者建议及讨论纠正

开发者建议：打开卡牌可以看到其中的效果实体；卡是效果容器，主力是效果编辑器。普通作者编辑 handler 内的行为，由 ins/orc 生成 csx 填入 handler，其余编排保持不变。预制体可由 agent 制作。

最初曾提出“复杂机制必须自动生成编排”，用户指出这个论证过度。例如可以用两个效果实现：受伤计数效果在 handler 中维护计数；部署效果的 handler 给本单位添加前者。**不能因为机制复杂，就判定必须开放触发器制作或重建编排。** 状态变量的归属与清理仍需按后端实际规则确认，不能直接假设为进程全局变量。

随后用户指出，自动拆效果、连接效果也需要和后端高度集成，编排困难。手工不断补模板和参数的维护量又过大，因此提出等待效果实体预制体规范化后，考虑开发扫描生成。引擎开发者反馈这部分仍需考虑。

**当前没有预制体规范、目录接口、扫描方式或自动编排的定案。用户已明确要求先讨论不依赖这些结论的内容。不要反复追问同一组后端问题，也不要先行开发扫描器。**

## 创作链整合的调研基础

现有两条链：

- 引擎原生 C#：分词 → AST → 语义映射 → DSL → 模板生成脚本。
- 工坊移植 JS：旧 Kards-Desktop 的 OrC 解析器、组合器和 Inspector 模型 → 效果图 → `DesktopNativeLowering`／`DesktopNativeCodegen` → 引擎执行。JS 负责创作，不能因此认定对局由 JS 推进。

建议方向是复用 JS 的句式和语料，逐步统一 handler 行为、原语契约和编译后端；不是立即把 JS 全部翻译成 C#。当前 C# DSL 固定字段模型不足以直接无损承接全部工坊表达式，不能强行压缩后宣称整合完成。上述仍属设计建议，不是已实现架构。

代码入口：

- `proto/bridge/Kards.Ui.OrcBridge/DesktopOrc.cs`：JS 宿主与解析请求。
- 同目录 `DesktopNativeLowering.cs`、`DesktopNativeCodegen.cs`、`DesktopNativeAliases.cs`：执行适配和代码生成。
- 同目录 `DesktopNativeRuntime.cs`：宿主运行辅助门面，部分生成脚本依赖它。
- 同目录 `InspectorDocument.cs`、`InspectorComposition.cs`、`DiyCapability.cs`：编辑数据、组合和能力判据。
- `proto/ui/screens/NativeEffectInspector*.cs`、`InspectorComposer.Details.cs`、`DiyEffectEditorScreen.cs`：界面入口。
- 相邻引擎 `src/Orc.Game/EffectParsing/`：原生解析、DSL、模板与编译驱动。

### 新发现的契约缺口（需反馈引擎侧，界面绕不过去）

1. **读不到被遍历实体的属性**：`read.of` 封闭集只有 `self`／`viewer`，`iterate as t` 之后没有任何表达式能读 `t` 的防御力。于是「若目标防御 ≤ 2」这类条件**写不出来**；`script` 也救不了（v1 脚本无值通道）。
2. **没有「查询某方所有单位」的原语**：26 个节点全是动作，`OwnerUnits` 被列入 EXCLUSIONS，`iterate.over` 只能来自 `ask`（要弹窗）或视图里的 `entity[]`。
3. `choice` 运行期抛 `NotSupportedException`（等前端桥接 S10）；`ask.prompt`／`kind` 运行期未使用。
4. `JoinFrontlineAsync`／`JoinSupportLineAsync` 在 EXCLUSIONS 的「延后」区，补 `[HandlerDslResult]` 即可进目录——「把单位塞进战场」的核心动作，值得催。
5. 目录只有英文 `Name`，没有中文显示名；对「不懂代码的玩家」是硬伤，建议引擎加 `title`（增量变更，只升 `catalogRevision`）。
