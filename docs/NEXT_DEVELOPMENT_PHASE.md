1. 规则、效果执行、目标合法性、资源变化与胜负完全归 OrC-KSD。原版 KARDS 的差异作为参考和能力需求，不自动转换为 UI 规则。
2. 上游仓库为 [Shangt1145/OrC-KSD](https://github.com/Shangt1145/OrC-KSD)。当前桥接默认引用 `H:/Working Folder/OrC-KSD-github/src/Orc.Game`。交接记录的引擎提交是 `73f76ab`；本轮未独立验证该工作区 Git 状态，不能把它当作已核实的干净版本。
3. **收到用户的更新提醒后才重新拉取。** 拉取前读取 HEAD 和工作区改动；存在本地改动时保留并核对，不直接 reset、checkout、覆盖或自动合并。交接记录提到的部署候选改动需要单独处理。
4. 更新后先阅读变更与相应架构分册，检查公开 API、信号含义、载荷、时序、生命周期、效果格式及运行依赖，再调整桥接。不因 API 名称未变就认定兼容。
5. `架构docs` 是上游提供的契约依据；发现源码分歧记录在接入报告，等待确认，不直接改写这些文档消除差异。
6. 保留一个统一真实对局入口，通过对局模式配置真人双座位或本地对手；探针、固定起手及自动选择仅用于显式测试/演示配置，不成为产品行为。

建议新增一份**轻量接入基线记录**：仓库 URL、完整提交号、是否有本地改动及其摘要、桥接契约版本、效果资源版本、验证结果。它不是运行时引擎对象，也不伪装成上游已经提供的版本 API。

扩展集中在 `proto/bridge/Kards.Ui.OrcBridge`：引擎对象和 Ref 的映射、卡池装配、事件翻译、能力适配均放在这里。`proto/contracts` 只传值对象，UI 只使用 DTO 和输入命令。新增 DTO 优先采用可选字段或新类型；重大语义变化显式升级契约和夹具，不让旧 UI 默默误读。

## 2. 能力差距与等待策略

下表是计划中的接入检查项，**不表示 OrC-KSD 已有这些 API**。能力状态建议区分 `Available / Unavailable / Unverified`，由桥接按经过验证的上游版本声明；不靠异常兜底猜测或 UI 规则探测。

| 能力 | 当前证据 | 处理 / 保留空间 |
|---|---|---|
| 单位指挥、行动候选 | 已有 `BeginCommandAsync` 和 `GetCommandAvailability` | 继续使用，复验失败由引擎报告 |
| 手牌打出可用性及拒绝原因 | 全部手牌被标可出，拒绝被合并 | 有上游纯查询才发布确定可用性；缺失时标为未知/可尝试，保留原因字段；不在 UI 用费用和词条重算 |
| 效果装配 | 上游有 Registry/Prefab；本地原始 `effects` 格式不同且未接入 | 导入层转换到上游认可格式，引擎执行；无法完整转换的卡明确列为未支持 |
| 段对应的历史状态 | 现 host 在消费段时读取实时终态 | 优先使用上游段完成快照或明确动作边界及时冻结；缺失则记录限制，不从晚到活对象猜历史 |
| 反制激活/实际触发/失活及公开资源 | 激活信号与原版触发语义不同；敌方资源直接读实际点数 | 等待或核实公开读面和时机契约；先接可验证路径，完整反制上线受此项约束 |
| 空牌库结算 | 当前按空集合契约抛错 | 原版疲劳为待上游能力；不在 UI 计数扣血。阶段验收分别记录支持路径与空牌库限制 |
| 自定义兵种与邻位规则 | 未映射兵种被裁掉；前线表现顺序独立于槽位 | 未知类型显式报告；新增规则读取位置时重新绑定表现与规则位置，不强转成已有兵种 |
| 战斗伤害/致死预览 | 当前预览数值为空 | 可以做候选高亮；只有上游提供预览才显示数值和骷髅，不以攻防相减代替 |

未来增加退却、生成、发现、连续选择、Forecast 等能力时，优先扩展请求映射及事件载荷。天气和特殊卡规则继续由引擎实现。

### 6A：先修玩家实际碰到的一层

- **落点与审计**：对照 `FrontDrop`、`PlaceOnFront`、绘制位置和真实拖拽结果。前线以目标卡左右关系、最终行顺序和紧凑居中验收；槽位重复本身不是失败。支援线保留槽位顺序及 HQ 的规则位置。仅在引擎认可候选中提交，不把前线的表现重排方式套到支援线。
- **失败忠实性**：玩家指向无效/失效目标时显式拒绝或重新选择，不能 `AutoRespond` 改成总部或第一个目标。保留引擎拒绝原因，缺少原因时表达未知原因，不猜“费用不足”。
- **消费与历史值**：每场对局只消费一次 `TakeSegments()`，按序冻结并分发给表现和两座位视图。修复“战斗 impacts 覆盖同段抽牌/指令步骤”。复用现有 `SegmentPlayer` 的串行及取消原则，确认其与真实表现载荷如何对接，不建立第二条互相争抢的消费链。
- **交互与播放解耦**：真实操作连续提交、按最新引擎投影判断；动画按历史快照依次播放，新操作不打断或快进上一段。布局移动包含在 FIFO 完成边界，重建画面不丢失按住的手势。引擎请求自身仍受互斥保护；挂起中的目标请求拥有独立应答通道，不能因动作队列正等待该请求而无法提交答案。
- **生命周期**：对局有唯一 MatchId，座位是观察者上下文；重新开局使用新的对局身份。退出/重开时取消本局任务、断开订阅、清理待选请求和瞬态表现，迟到事件不得影响新局。
- **边界**：把 `OrcMatchRunner.ActiveSeatOnTurn` 的引擎读取移入桥接；增加 UI 源码/程序集依赖护栏。

主要落点：`OrcMatchHost.cs`、`OrcMatchSession.cs`、`OrcActionReader.cs`、`OrcMatchRunner.cs`、`BattleScreen.cs`、`BattleScreen.RealCapture.cs`、`Main.cs`。避免先按文件行数拆分，先稳定职责与行为。

部署候选“相邻空槽 / 全部空槽”仍是上游契约分歧。两个分支都只能由桥接消费引擎返回的候选，UI 不自行扩充候选。引擎测试的历史 38 条失败按原因归类并保留记录；不能统一改断言制造全绿，也不能仅以“数量仍为 38”认定无回归。

### 6B：从现有声明到真实引擎效果

导入链建议：

```text
本地卡池的基础定义 + 原始 effects
    → 资源导入层：结构检查、文本核对、原语/目标/条件转换
    → 上游认可的 DSL / Prefab / Registry 声明
    → 对局初始化前装配
    → OrC-KSD 执行效果并发出事件
    → 桥接冻结可见数据，UI 播放
```

不在 `UiCardDefinition` 塞入运行时 Effect、Ref 或 csx 执行器；UI 所需的卡面文本与“该卡可否在当前支持集使用”可以独立投影。效果原始格式、版本与转换诊断留在导入/桥接侧。

卡片状态建议至少分为：基础定义可表示、效果声明可转换、语义已核验、对局可用、仅生成、未支持。报告既包含结构覆盖率，也包含语义完整覆盖率。未知词条、类型、目标、条件、时机、生成卡引用或脚本失败明确报告，不能静默裁剪。动态生成的牌也必须带上已验证效果装配。

先建立约 12–16 张经审核的代表支持集，再逐批扩展。以下是真实卡 ID 的候选，不是已承诺支持：

| 候选 | 验证目的 | 接入前注意 |
|---|---|---|
| `USG/commands/27` 工业生产 | 资源槽变化 | 结算时机与上限由引擎控制 |
| `deran/command/_12` 突袭、`USG/commands/_11` 轨道轰炸 | 单位选靶、定值伤害、致死 | 必须是选中的目标，不能替换为 HQ |
| `av76/command/-10` 新地及卡尔拉研发 | 选项选择、生成手牌、token 引用 | 核验两个分支及生成牌的声明依赖 |
| `av76/command/-1` 经济复苏 | 多动作：资源加抽牌 | 原始卡是 token，只能作为生成/测试案例 |
| `USG/commands/_13` 解体 | 友方死亡触发反制及 HQ 伤害 | 依赖真实反制触发契约，不能在武装时执行 |
| `av76/command/-14` 远程打击 | 拦截部署效果 | 待上游时机确认，不作为第一批必须通过项 |

另外选取基础兵种、已支持词条、部署触发、死亡触发、群体效果及临时修饰器各类单位/指令覆盖场景。不能为达到张数塞入规则不完整的牌。

正常牌组只使用“语义已核验且允许组牌”的卡。先移除“必须含指令”的无依据强制条件、过滤生成卡，再使用经过核验的作者牌组。30 张、同名上限及阵营规则在上游确认前维持为项目策略并明确标注；不直接改成原版 39 张抽牌池或用低费加权掩盖随机起手问题。固定起手只保留在审计配置。

**6B1 已交付**：9 种完整单位声明入审核清单；真实入口要求源声明哈希与 UI 定义一致，拒绝未装配效果、生成卡及缺失数值。首批支持集最多 27 份，不足正常 30 张策略，故本地真实入口暂使用标注为 24 张的验证牌组；正常 30 张策略保留，容量不足明确报错。此配置用于验证支持集，不承诺原版 KARDS 组牌。详情见阶段验收。

### 6C：统一真人选择与反制生命周期

优先复用 `UiTargetRequest`、`UiChoiceSlot`、`IUiTargetResponder`，补足上游允许的呈现与取消语义，替换只承载卡片的 `PendingChoices` 单一路径。请求标识关联对局、座位和当前请求，支持引用、标识选项、卡牌定义及连续请求。

- 真人模式提交后检查 `Complete` 返回值。`false` 保留面板与请求，提示可纠正原因并允许重试；取消按上游允许的阶段执行。测试自动应答策略与真人策略分开。
- 数量、成员、类别、失效目标最终由引擎复验；UI 仅按请求的 Min/Max 控制确认按钮。
- 选择期间封锁无关行动，但允许请求应答。已提交动作之后出现的选择不能擅自回滚已部署单位；取消后果以引擎结果为准。
- 候选高亮与箭头先交付。伤害数字、致死骷髅只有在上游预览能力可用时接入。
- 反制区分“武装 / 解除 / 真实触发 / 未触发失活”，不能直接用当前 `counter.triggered` 字符串判定公开揭示。核验实付/退款、触发优先级、手牌保留、消耗和再武装。
- 对手投影、事件、历史、资源 HUD 和座位切换均遵循可见性读面。若上游没有反制费用的公开投影，先记录并限制完整功能上线，不自行编造敌方资源账本。

### 6D：从能看双方到双方都能操作

每条命令携带或由 session 绑定明确行动座位；行动权限在桥接层验证。两座位共享同一引擎对局、同一事件消费源，各自获得可见投影；切换时遮挡上一方手牌和瞬态详情。

真人双座位模式双方完成换牌、各自提交行动；`EndTurn` 不启动 AI。对手驱动只在明确的单人模式启用，并通过相同的引擎接口运行。不能通过 UI 对引擎数据直接写入来“让对手行动”。

完整对局测试使用已核验牌组与确定场景，真正执行双方部署/移动/攻击/指令。断言终局、胜方、原因、禁止继续行动及重开清理。随机种子测试附限时和失败轨迹，不以结束回合次数推断已完成，更不能只输出日志或遇到无牌可出就提前返回通过。

## 4. 验收矩阵

每项均记录“通过 / 失败 / 依赖上游未具备”，最后一种不是通过。

| 类别 | 代表场景 | 判据 |
|---|---|---|
| 手势与布局 | 空行、1–4 单位、仅余一个位置；左侧/两牌之间/行尾；1280×720 与 1600×900 | 高亮、松手与最终行位置一致；HQ 与规则槽位顺序一致；前线满员正确拒绝 |
| 拒绝和取消 | 不足资源、非法目标、过期请求、重复提交、右键/Esc（项目约定） | 无静默改靶；无非法扣费/状态改变；请求可重试或正确结束 |
| 混合效果 | 伤害加抽牌、死亡加触发、群体结算、延迟效果 | 一次消费、顺序正确、无漏播/重复；最终投影等于引擎状态 |
| 选择 | 单选、多选、零选择、标识选项、生成卡、连续两个请求 | 对应正确请求和座位；终结恰一次；非法答案不永久 park |
| 反制 | 武装、解除、条件命中、未命中失活 | 费用守恒、实际时机正确；揭示前无身份或费用泄露 |
| 双座位 | 双方换牌、双方部署/攻击、结束回合、视角切换 | 非行动方拒绝；无真人模式自动代打；不抢消费事件 |
| 终局与重开 | HQ 致死、投降、动画/选择期间退出、重新开局 | 真实胜负断言；无悬挂任务及旧局数据串入 |
| 上游升级 | 初始化、部署、指挥、选择、效果装配、退出、依赖复制 | 明确记录 API 与语义差异；已有场景无新回归 |

验证分三层：有强断言的桥接/契约测试；无界面加载与资源验证；走真实输入入口的图形审计和人工看图。6A 已为 `--verify-ui` 增加投影夹具的真实输入矩阵，其中真实引擎检查仍直接提交命令，不能替代真实牌组图形手势验收。音画时机另以可核对录像验收，不从宣传剪辑推导精确时长。

## 5. 本阶段之后

- 表现完善：原版伤害预览、HQ 终局、武器级动画/音效覆盖、换牌过渡、历史与词条反馈；先补缺失原版证据，再调参数。保留现有砸地设计约定。
- 卡池扩展：按语义测试覆盖增加效果原语、词条及自定义类型；连续选择界面为发现、研究和天气等机制留入口，上游能力到位后接入。
