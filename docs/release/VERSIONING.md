# 版本号规则

日期：2026-10-05。

## 格式

```
MAJOR.MINOR.PATCH[-预发布标识]
```

## 核心原则：预发布不占号

**alpha / beta 阶段三位数字恒为 `0.0.0`，只递增后缀序号。**
首个对外发布即为 `0.1.0`；三位数字**从那一刻起**才开始递增。

这样做的原因：预发布阶段的改动是连续且不稳定的，若每个测试版都占用 MINOR/PATCH，正式版号会失去"对外承诺"的含义。

## 各段含义（0.1.0 起生效）

| 段 | 含义 | 何时 +1 |
|---|---|---|
| **MAJOR** 大版本 | 架构/契约不兼容的变更 | DTO 契约重定义、引擎桥接面不兼容、需要上游同步改造 |
| **MINOR** 小版本 | 向后兼容的新功能 | 完成一个阶段（新增演出阶段、接入新的引擎能力） |
| **PATCH** bug 修复版本 | 只修问题，不新增功能 | 修复渲染/演出/桥接缺陷，不引入新行为 |

## 预发布标识

| 标识 | 短写 | 形态 | 用途 |
|---|---|---|---|
| alpha | `A.N` | `0.0.0-alpha.N` | 功能未完整、契约可能变的测试版，N 从 1 起 |
| beta | `B.N` | `0.0.0-beta.N` | 功能已完整、进入打磨与回归的测试版，N 从 1 起 |
| hotfix | — | `0.1.0-hotfix` | **已发布版本**上的紧急修复，三位编号不变；同版本第 2 次起 `-hotfix.2` |

**优先级**（由低到高）：

```
0.0.0-alpha.1 < 0.0.0-alpha.2 < 0.0.0-beta.1 < 0.1.0 < 0.1.0-hotfix < 0.1.0-hotfix.2 < 0.1.1
```

即：alpha → beta → 首个正式版 `0.1.0`；正式版之后的紧急修复排在下一个常规版本之前。

## 规则要点

1. **预发布期间不递增三位数字**：`-alpha.N` / `-beta.N` 的 N 只是测试版序号，不代表功能量。
   **例外（2026-10-24）**：整代重写允许用 `X.0.0-alpha.N` 宣告，只放行 MINOR/PATCH 均为 0 的形态
   （例：手机版独立成代 → `2.0.0-alpha.1`）；`0.1.2-alpha.1` 这种"既占号又预发布"的写法仍然禁止。
2. **hotfix 不占号**：修的是已发布版本，编号不变只加后缀；该修复**必须同时合回主干**，并在下一个常规版本（PATCH 或 MINOR）中体现，不重复发号。
3. **预发布期不走 PATCH**：alpha/beta 期间的修复直接体现在当前预发布号（递增 N）；PATCH 与 hotfix 只用于已发布版本。
4. **0.x 阶段契约未冻结**：`0.x.y` 的 MINOR 允许不兼容变更，但必须在阶段文档里写明。**1.0.0 起严格执行上表**。
5. **单一真源**：根目录 `VERSION` 文件，同步写入 `project.godot` 的 `application/config/version`；UI 页脚直接读该设置显示，避免两处不一致。
6. **打标**：每个对外版本打 `v<VERSION>` 标签（如 `v0.0.0-alpha.1`）。

## 操作

改版本用脚本，不要手改两处：

```powershell
& 'H:\Working Folder\OrC-KSD.Godot\tools\version.ps1' -Get
& 'H:\Working Folder\OrC-KSD.Godot\tools\version.ps1' -Set 0.0.0-alpha.2
```

脚本会校验格式（含 `0.0.0-alpha.N` / `0.0.0-beta.N` / `x.y.z-hotfix[.N]`）并同时更新 `VERSION` 与 `project.godot`。

## 发行规则（全量与增量）

2026-10-24 补。此前这里只规定"版本号叫什么"，没规定"包怎么发"——于是出现 11 个发行目录只有 3 个有 tag、
单来源补丁 943 MB、tag 与二进制对不上的局面。以下规则由 `tools/check-consistency.ps1` 机器核对。

### 1. 每次发版必须产出四件套

```
dist/releases/<版本>/
  full/         OrC-KSD-<版本>-win-x64.zip                                   完整包（新玩家）
  patches/      OrC-KSD-<版本>-from-<源构建12>-to-<目标构建12>.orcupdate      增量（老玩家）
  notes/        发行说明 + offline-update-report.json
  verification/ 导出、离线更新、升级后 EXE、工坊 四份日志
  SHA256.txt    相对本目录的校验和
```

**全量与增量每次一起出**，不允许"这次只给补丁"或"这次只给全量"。

### 2. 增量的基线只认上一个已发布版本

- 主基线＝`dist/releases/<上一版>/full/*.zip`（或归档目录 `H:\g\baselines`）。
- 需要跨版本兼容时显式 `-AdditionalBaselineZips`，**且每个分片 ≤ 150 MB**；超了只发全量，不发补丁。
- 反例（2026-10-24）：beta.1→beta.6 兼容分片单个 **943 MB**，合集比完整包还大——禁止再这么发。

### 3. 发版顺序是硬约束

| 步 | 动作 | 为什么 |
|---|---|---|
| 1 | `git status` 为 0 | 有未提交改动时出的包对应不到任何提交 |
| 2 | `tools/version.ps1 -Set <版本>` | 版本号唯一真源，同时写 `project.godot` |
| 3 | `tools/release.ps1 -BaselineZip <上一版 zip> -SingleBaseline` | 出包 |
| 4 | **提交**（版本号 + 发行说明） | 让包有对应 commit |
| 5 | `git tag -a v<版本>` | 打标 |
| 6 | push 分支 + tag | 远端可追溯 |
| 7 | GitHub Release 指向该 tag | 资产＝补丁 + notes + SHA256；全量 >1 GB 不传，说明里指路 |
| 8 | `tools/check-consistency.ps1` → `CONSISTENCY_OK` | 收工前最后一道门 |

### 4. 命名一一对应

| 载体 | 形态 | 示例 |
|---|---|---|
| `VERSION` | 版本号原文 | `0.0.0beta7.hotfix.3` |
| 发行目录 | 与 VERSION 完全相同 | `dist/releases/0.0.0beta7.hotfix.3/` |
| git tag | `v` + VERSION 原文 | `v0.0.0beta7.hotfix.3` |
| Release 标题 | VERSION 原文 + 摘要 | `0.0.0beta7.hotfix.3 — 烟幕生命周期修复` |

### 5. 禁止事项

- 禁止在未提交的工作区出包（本轮乱象主因）
- 禁止把 >150 MB 的分片当增量发布
- 禁止手改 `RELEASE_INDEX.md`（由脚本生成）
- 禁止同时开两个"正在发版"的树；一次只有一个窗口在改代码
