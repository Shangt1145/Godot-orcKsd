# 原版 KARDS 调研与 OrC-KSD 接入差距

日期：2026-10-07。配套开发计划：[NEXT_DEVELOPMENT_PHASE.md](NEXT_DEVELOPMENT_PHASE.md)。

本轮重新查阅官方玩法、帮助中心及近期更新，核对本项目的桥接代码和原始卡池。未启动原版客户端，未新增录像、逐帧时长或声音测量。旧录像观察沿用 [KARDS_SELECTION_RESEARCH.md](KARDS_SELECTION_RESEARCH.md) 和 [KARDS_BATTLE_RESEARCH.md](KARDS_BATTLE_RESEARCH.md)，其观察与推断仍须区分。

**开发边界：以 OrC-KSD 引擎为规则与运行时真源。** 用户在本轮明确说明：引擎源码在 GitHub，更新后会提醒重新拉取。本轮未拉取、修改或提交引擎。原版 KARDS 是交互与表现参照；规则差异记录为兼容性差距，不由 UI 补算，也不据此擅改上游。

## 1. 原版已核实的行为

| 主题 | 官方行为 | 对项目的意义 |
|---|---|---|
| 前线 | 最多 5 个单位，同一时间由一方控制；敌方占据时不能移入；从支援线拖入 | 容量、归属、合法目标来自引擎；UI 表达落点、邻卡让位和控制权变化。[前线说明](https://support.kards.com/hc/en-us/articles/360026464712-Battlefield-elements-The-Frontline) |
| 支援线 | 每方 HQ 加最多 4 个单位；从手牌拖入；费用不足或满线有错误反馈 | 拖拽预览应使用引擎候选；紧凑排布不能改变规则位置。[支援线说明](https://support.kards.com/hc/en-us/articles/360026757171-Battlefield-elements-The-Support-Line) |
| 开局和手牌 | 先手 4 张、后手 5 张；换下的牌回牌库；手牌上限 9 张，超出抽牌弃置；敌方手牌隐藏 | 换牌结束重读投影；爆牌不播放“进入手牌”；不展示敌方牌面。[手牌说明](https://support.kards.com/hc/en-us/articles/360026500332-Battlefield-elements-Hands) |
| 空牌库 | 尝试从空牌库抽牌会伤害 HQ，后续回合开始抽牌的伤害递增 | 与当前引擎空集合抽牌抛错不同，列入上游能力差距；UI 不实现疲劳计数。[手牌说明](https://support.kards.com/hc/en-us/articles/360026500332-Battlefield-elements-Hands) |

| 指令 | 拖出、付费、可能选择目标、结算、弃置；被反制仍付费；存在即时及延迟效果 | 指令提交、目标请求和效果装配必须形成同一条引擎链路。[指令说明](https://support.kards.com/hc/en-us/articles/360026754851-Orders) |
| 反制 | 武装后仍在手牌；解除退费；下一敌方回合按条件触发并揭示弃置，未触发则失活；敌方看不到身份及武装费用变化 | 不仅是武装动画：还需要触发时机、失活、退款和资源可见性契约。[反制说明](https://support.kards.com/hc/en-us/articles/360026404872-Countermeasure) |
| 守护 | 保护同线相邻单位及 HQ，炮兵和轰炸机可绕过 | 位置具有规则意义；不能把紧凑绘制后的相邻关系当引擎守护关系。[守护说明](https://support.kards.com/hc/en-us/articles/360026238532-Unit-ability-Guard) |
| 组牌 | 普通、限定、特殊、精英的同名卡上限分别为 4/3/2/1；官方说明总计 40 张，模式说明明确 39 张加 1 HQ；盟国最多 12 张 | 当前 30 张、统一最多 3 张是项目现有策略，不应称为原版组牌规则；本轮只记录差异。[卡牌说明](https://support.kards.com/hc/en-us/articles/360026768151-Cards)、[模式说明](https://support.kards.com/hc/en-us/articles/27800508740249-Game-Modes)、[玩法](https://www.kards.com/how-to-play) |

注意官方资料也有表述差异：玩法总览把 Fury 概括成两次行动，专门帮助页及 Homefront 战斗词条说明写的是每回合攻击两次。因此原版调研采用后两者的具体描述；OrC-KSD 的实际行为仍由其源码、契约及测试确定，不在 UI 实现词条判断。[Fury 帮助](https://support.kards.com/hc/en-us/articles/360026228852-Unit-ability-Fury)、[战斗词条](https://www.kards.com/news/homefront-combat-keywords)

官方支援线文章没有说明每一个空位置的插入算法，不能用它直接裁决本项目“相邻空槽 / 全部空槽”的分歧。该问题需要按上游约定确认。

## 3. 原版交互证据与项目决策分开

旧实机调研已观察到：拖拽部署与攻击、红色瞄准箭头、非目标灰化、红色伤害徽章、换牌红叉、等待对手横幅、指令侧边展示。见 [选择调研的时间码](KARDS_SELECTION_RESEARCH.md)。本轮没有重新测量这些录像。

以下仍属于待补证据或项目既有决策，不能写成“原版完全如此”：

- 指向指令直接从手牌拖到目标的完整流程；部署后自动进入瞄准的时机。
- 指令停靠与交叉剑卡背的归属规则。
- 右键、Esc、拖回原位的原版取消条件，以及每一提交阶段的取消后果。
- 多选、连续选择、非法提交和目标失效时的完整反馈。
- 无剪辑录像中的缓动、时长、命中帧、声音同步。

项目已定的紧凑居中行布局、前线“盒子与让位”、拖拽操作、按防御值决定砸地力度继续作为本地表现约定。其合法性、容量和位置语义由引擎投影约束；未来引擎若增加前线相邻规则，需要重新检查表现顺序与规则顺序能否分离。

## 4. 本轮新核实：卡池有声明，尚未装配

本轮直接读取 `proto/data/nations/*.json` 的 `cards` 对象，排除不含 `cards` 的 `_meta.json`，统计结果如下：

| 项目 | 本轮静态核对 |
|---|---:|
| 卡片总数 / 唯一 ID | 315 / 315 |
| 单位 / 指令 / 反制 | 161 / 150 / 4 |
| 非空 `effects` 声明 | 255 |
| 非空单数 `effect` 字段 | 0 |
| 标记为 token 的卡 | 84 |

**更正交接记录 §4.5：不能由单数 `effect` 为空推断“卡池没有效果数据”。真实字段是复数 `effects`。** `CardCatalog` 没有读取它，`UiCardDefinition` 没有承载效果声明，`CardPoolCompiler` 只编译基础定义与词条，创建对局也未装配 `effectRegistry`。这是效果数据到运行时的断链。

这些声明是 `{trigger, actions, targets, ...}`，与架构文档规定的 `{template, fills}` DSL 不是同一格式。需要在资源导入/构建层核对、转换成引擎可接收的定义；UI 不执行 `actions`，不另写伤害、抽牌或反制规则解释器。

**255 是声明存在数，不是语义覆盖率。** 已发现至少三处需要审核的例子：

| 卡片 | 卡面与声明的差距 | 处理 |
|---|---|---|
| `deran/command/_1` 搜查 | 卡面有揭示隐蔽单位；声明仅抽牌 | 未补齐并经引擎验证前，不标为完整支持 |
| `deran/command/_10` 停火 | “双方抽两张牌”分支只有 `side:self` 的抽牌 | 核对漏项及双方结算次序 |
| `USG/commands/_3` 战前动员 | 群体强化有剩余指挥点条件；当前对应动作未表达该条件 | 核对条件是否遗漏，避免无条件强化 |

上述核对是静态审查，没有在引擎中执行这些声明。Token 数 84 与交接中“编译池里 84 张指令/反制不可提交”恰好相同，二者是不同统计口径，不可混为一组。

## 5. 桥接现状与开发约束

本轮源码读取确认：

- `OrcActionReader` 把当前玩家全部手牌放入 `PlayableUids`；单位行动候选来自引擎查询。尚未获得手牌可打出查询时，应表达未知，不能自行补规则或假装查询成功。
- `OrcMatchSession.PlayAsync` 只接受 `UnitCard`；`ChooseTarget` 返回拒绝。真实指令与通用选择还未接通。
- `OrcMatchHost.Pump` 消费破坏性 `TakeSegments()`；有战斗 impacts 时跳过同段其他表现步骤。复杂效果上线前必须解决混合事件漏播和顺序问题。
- 第二座位有单独 host，但提交仍经过原 session，结束回合会自动驱动对手。双人模式目前不能仅靠换视角认定完成。
- `OrcMatchReader` 直接投影敌方真实剩余资源；接反制前需要确认上游公开资源读面，避免武装费用泄露。单纯隐藏手牌身份不足以满足原版要求。
- `DeckBuilder` 使用 30 张及统一 3 张上限，强制含指令，未按 `token` 标签过滤。支持集、生成卡和组牌策略必须分开。

引擎空牌库抽牌现有源码调用 `Deck.DrawInstance()` 并按空集合契约抛错。引擎 `counter.triggered` 在现有实现中用于反制激活分支；不能把这个信号直接视为“敌方动作已被反制并应公开揭示”。依据 [03 卡牌管理](../架构docs/03-卡牌管理.md)、[04 打出与部署](../架构docs/04-打出与部署.md) 及本轮读取的引擎源文件。需要上游提供或明确对应语义，而不是按字符串猜测。

现有 `UiInteraction` 已有请求 ID、槽位名、Min/Max、Reference/Option/CardDefinition，可优先复用。`Complete=false` 表示拒绝但请求继续等待；真人模式不能自动替玩家选择第一个目标。依据 [06 目标选择](../架构docs/06-目标选择（异步倒置）.md)。

## 6. 验证范围与下一阶段结论

[HANDOVER.md](HANDOVER.md) 记录 alpha.11 的 UI 99/99、无界面 8/8，以及引擎 765/803。**本轮未重跑这些测试**；它们是历史基线。交接中 `move=BROKEN[2,0,2]` 也不应直接作为算法失败结论：当前审计只用引擎槽位是否互异判断方向，前线需要验证最终画面顺序。

优先完成“手势提交可靠 → 引擎效果可执行 → 请求能由真人回答 → 事件与最终画面一致”的闭环，再扩展特效与全部卡池。缺少的引擎能力单列、保留接口，等用户提醒更新后重新检查，不用本地规则补丁绕过。
