# DIY 工坊 UI 案例调研：KARDS、制卡工具与规则组合

日期：2026-10-21。阶段：制作前调研；本轮未修改 UI 代码、未制作新界面、未打包。

## 1. 结论先行

工坊应该延续 KARDS 的卡牌浏览与材质语言，同时具有制作工具的清晰任务流程。不能把换成军绿、加几张卡图、把 JSON 树压紧一点当作完成设计。

本轮对上一版方案作出四项调整：

1. **浏览和制作切换工作状态**。浏览卡包时以卡面网格为主；进入单卡制作后突出编辑与大预览，卡库可以收起。取消默认同时展开“卡库＋长表单＋大预览＋诊断”的布局假设。
2. **规则编辑采用通用组合**。时机、对象范围、条件、目标、动作和值各有明确表达，不把底层 API 一对一铺成输入框，也不提供一批具体卡牌专用触发模板。
3. **复杂性按上下文出现**。编辑卡牌时看到卡牌属性，编辑规则时看到规则参数；身份、版本、源路径、lock 与原生声明进入信息／高级面板。
4. **先验证完整制作路径**。导入、寻找内容、编辑、预览、修正错误、存草稿、生效、试打、重开都要可操作，不能只展示一张静态漂亮卡面。

以上是针对本项目的设计判断，不是原版游戏存在这些 DIY 功能的声明。

## 3. 原版 KARDS：该学什么

### 3.1 先展示对象，再展示对象上的操作

官方卡组图中，大幅卡背组成网格，选中对象的封面与操作集中在旁侧。构筑示意图把搜索／费用筛选、卡池和紧凑名单划成清楚区域。这里值得借鉴的是视觉主次和对象上下文，而非把每个旧按钮照搬。

![KARDS 官方构筑分区图](../../artifacts/research/workshop-ui-20261021/kards-builder.png)

图源：[官方新 UI 说明](https://www.kards.com/news/new-user-interface)。这张图是官方发布的分区展示图，存在拼接和裁切，不能用于测量当前客户端像素坐标。

**本项目采用：** 卡包列表用真实卡面／封面与名称辨认；点击后在详情中显示编辑、导出等操作。卡包、扩展包和卡牌不退化成纯文字下拉列表。

**不照搬：** 商城货币、通配卡合成、国家进度、好友、排名与联网入口。没有对应功能就不做占位面板。

### 3.2 筛选要可发现，也要可收起

官方帮助呈现名称搜索，以及按类型、国家、稀有度筛选。筛选回答的是“我要找哪张”，不该与“我要修改这张的哪项属性”混成一页。

**本项目采用：** 搜索位于卡池顶部；展开筛选有明确入口，已选条件显示为可移除项，并提供清除。切换编辑卡牌时保留筛选与滚动位置。

**项目扩展：** 国家选择覆盖后端与自定义内容；带图标和名称，并有新建国家入口。不能照着截图把国家固定成原版有限集合。

### 3.3 单卡详情给卡面足够空间

官方详情图将大卡面与说明放在一起，当前操作紧邻当前卡牌。用户不需要从长表单顶部来回寻找一张很小的预览。

**本项目采用：** 当前卡牌的大预览、卡名、状态始终明确。图片导入和裁切时，预览就是操作中心；规则编辑时，它是结果参考，不挤占主要表达空间。

### 3.4 材质建立层级，不能压住信息

官方图使用木桌背景、旧纸卡面、深色面板和暖色强调。卡牌仍是最鲜明的视觉对象。

**本项目采用：** 背景纹理留在背景；正文与控件使用稳定的深色底；主要操作和选中对象才强调。不要给每一段都铺高对比金色标题条，也不要用背景地图替代分组和留白。

**卡面约束不变：** 单位／指令／反制自动切换 Astral 母版，字体、位置与裁切参考用户提供模板；本轮不改对局布局。

### 3.5 选择动画使用用户原片

重看的分解图显示卡牌在正面状态下横向展开、选择后汇聚，而不是普通菜单的翻面、缩小淡出。本次不重新虚构动画参数，也不把浏览大量已保存卡包的网格当成每次都要播放抉择。

**本项目采用：** 首页“卡包／扩展包”和其下一步选择保留抉择式过渡；实际编辑动作保持直接。重命名、保存、输入数值不重复播放大动画。

## 4. 专业制卡案例：制作工具应有的组织

### 4.1 Card Engine：集合管理与图形编辑有不同关注点

官方手册把卡牌集合、回收内容、模板和图像属性分别组织；提供复制、导出与撤销等工具。本轮实际查看了集合截图，以及模板、图像属性的示意。

**本项目判断：** 借鉴“当前对象＋相关工具”的组织；图片尺寸、裁切和对齐只在卡图制作时出现，草稿恢复有可见入口。不要照搬自由排版软件的全部坐标、图层和打印选项，逼用户先学习图形软件才能做一张可玩卡。

![Card Engine 手册中的集合与回收区](../../artifacts/research/workshop-ui-20261021/card-engine-collection.png)

图源：官方手册物理第 10 页，v0.11。图中的回收区是其制作工作流参考，不代表我们已经支持后端历史版本恢复。

### 4.2 Magic Set Editor：按整套内容组织作者任务

原作者说明确认其围绕制卡、整套统计和导出组织。可借鉴的是“作者正在制作一个集合”，不能把工坊设计成一堆不相关的临时单卡。

**本项目判断：** 卡包身份、国家、词条、扩展归属和卡图资源都需要整体视图；批量检查应能回到具体卡牌。包 ZIP 导出的是可移植作品，不只是生成一组 PNG。

本轮没有其桌面交互截图证据，故不凭介绍推定最佳布局或直接模仿控件位置。

### 4.3 未作为已验证设计依据的候选

Card Conjurer 的公开 creator 页面已找到，但本轮获取到的页面壳不能证明当前编辑交互，未把它列为已实测案例。网络上同名镜像、旧版和模板站点也没有混作同一版本。

搜索出现的 `magicseteditor.com` 宣传页没有代替原作者项目作为技术事实来源。后续若需要参考更多工具，先核验作者和实际页面，再纳入。

## 5. 规则编辑案例：用组合表达能力，不暴露整套实现

Blockly 的官方原则明确反对盲目把全部 API 一对一转成积木，并区分字面值、表达式、语句与分类。其设计资料也讨论嵌套过深和按钮过多带来的理解成本。[设计原则](https://docs.blockly.com/guides/design/blocks/)

**以下是本项目的设计推论：**

- 规则总览用能读懂的摘要，打开某条后再编辑通用时机、对象范围、条件、目标和动作列表。
- 条件表达“全部满足／任一满足／取反”，动作表达按顺序执行；两者有不同结构和标识，不能只靠颜色辨认。
- 数值位置既能填常量，也能选择变量／计数／表达式，不能所有值都强迫写字符串，也不能只准填一个整数。
- 添加动作先进入分类与搜索，按相关上下文呈现可选项；未知内容不自动替换成目录第一项。
- 排序、复制和移除应可发现；常用操作可在选中项出现，避免每一行永久摆满四五个按钮。
- 已导入且暂不支持图形编辑的结构显示原始摘要、支持状态和高级入口，保持数据；“能显示”不等于“可编辑／可执行”。

**不用两种捷径：** 一种是平铺 target、band、event、priority 等技术字段；另一种是只提供几种具体触发案例，换一个机制就无法表达。我们需要通用的、后端支持范围内的组合语法。

不要求采用 Blockly 的自由画布或引入 WebView。现有 Godot Composer 可以吸收这些原则，实际执行仍由原生引擎完成。

## 6. 修订后的工坊结构

### 6.1 浏览卡包

```text
工坊首页（两张选择卡）
  → 创建／修改
  → 卡包卡面网格 + 搜索／筛选
  → 所选卡包详情：名称、来源、状态、内容数量、编辑与更多操作
```

导入是次级入口：选文件 → 显示真实内容和冲突 → 确认安装 → 打开该包。取消后返回原位置，不重置已有草稿。

### 6.2 单卡制作

```text
包名 / 当前卡牌                         未保存或草稿状态
属性 · 规则与词条 · 卡图 · 风味          保存草稿  生效

当前任务的编辑区                       当前卡面大预览
                                       当前检查结果摘要

卡库：可收起的列表／抽屉                 详细问题：按需打开
```

这是信息结构示意，不是已制作的视觉稿。工具栏必须给出明确语义；危险操作和导出留在更多操作，不横排占满屏幕。

与上一方案的区别：不默认让三大栏和详细诊断全部常驻；浏览对象与制作对象采用不同空间分配。

### 6.3 规则工作台

```text
规则摘要列表  →  当前规则

何时发生：通用事件与作用范围
条件：可选，可组合
目标：对象或对象集合
动作：可添加、排序、复制和移除

选中项的参数／表达式编辑
```

采用展开编辑或上下文面板，不把所有嵌套参数同时展开。高级结构能打开原文，但主要流程不要求用户先理解源文件路径、GUID 或 lock。

## 7. 交互状态是设计的一部分

| 场景 | 必须清楚呈现 |
| --- | --- |
| 新空卡包 | 当前为空，下一步是创建卡牌／国家／词条，而不是空白面板 |
| 改动未存 | 当前有修改；离开可继续编辑、保存或明确丢弃 |
| 保存成功 | 草稿已落盘，正式构筑是否变化需另行说明 |
| 检查失败 | 哪张卡、哪个规则、哪里不支持；点击定位；原内容不丢 |
| 转正成功 | 明确何时用于新构筑／新对局；不篡改正在进行的对局 |
| 转正失败 | 草稿仍可继续；旧正式内容是否恢复；有明确下一步 |
| 导入同一包 | 相同内容和替换更新分开，保留取消和备份反馈 |
| 中断草稿 | 已有包和未转正新包都能被发现、导出／备份；未实现 resume 就明确说明 |
| 自带内容修改 | 明确本机副本；原版来源与自定义覆盖不相互混淆 |

以上来自本项目后端语义及用户工作流，不把其他制卡软件的自动保存机制直接等同 AssetEditor 的转正。

## 8. 制作前的检验门槛

先做两种尺寸的可交互原型，再替换生产界面；原型必须标明哪些操作已接入真实后端，不能拿模拟成功提示充当完成。

至少覆盖：

1. 不读技术文档，完成“新建卡 → 改国家／类型／属性 → 导图 → 看清预览 → 保存草稿”。
2. 从大卡包里搜索一张卡、进入编辑、返回，搜索条件与位置保留。
3. 组合一种新规则；再组合结构不同的规则，不能依赖具体卡名或固定触发预设。
4. 导入带未知字段和复杂效果的卡，编辑已支持字段后无损保存；未知机制不能悄悄变成默认值。
5. 出现真实后端错误，能够定位、修复、再次保存；转正失败仍能继续编辑。
6. 1280×720 和 1600×900 中，主操作、输入、卡面与状态都可用；长中文名、长说明、多国家与多规则不挤坏界面。
7. 卡图、文字与单位／指令／反制母版一致；不修改战场布局。
8. 已有草稿重开、未保存取消离开、自定义国家和原图资源往返都完整。

首次视觉原型优先做“卡包浏览”“单卡属性”“规则工作台”三页，并在同一套实际内容上演示完整路径。认可的信息组织再落地到当前新引擎适配 T1–T6，不直接复用目前的通用 JSON 属性页作为最终设计。
