# 契约 check 向量：前端那一半终于跑起来了

> 2026-11-05。对应 `tests/HandlerDslVectorTests.cs` 与 issue #5。

## 1 一句话

> 契约包里 27 条 `check` 向量是**冻结的基准**，引擎侧一直在跑，我们这边没跑。
> 接上之后**首跑 21 过 / 8 败**——五处分歧，全在我们的判定口径上。

这些分歧没有一条会让画布打不开，也没有一条会让人立刻发现：它们只在「作者写错了一处」时
把**错误码或路径**报偏，而报偏的代价是作者照着提示去改，改完还是错的。

## 2 为什么向量比「我们自己的单测」值钱

| | 我们自己的校验器测试 | 契约向量 |
| --- | --- | --- |
| 目录从哪来 | 引擎扫描（会随引擎变） | **冻结快照**（自带 `catalog` 段） |
| 断言什么 | 我们觉得该报什么 | 契约规定该报什么 |
| 谁跑 | 只有我们 | **前后端各跑一遍** |

向量自带目录快照这一点是关键：它测的是**判定口径**，不是「引擎今天扫出了什么」。
所以引擎加节点、改引脚，向量不会红；但我们的判定跟契约不一致，立刻就红。

契约 README 的原话是「同一份非法 DSL，前后端报出的码与节点路径一致」是**测试期保证**。
只有一侧在跑，这个保证就等于不存在——它就是这次的 8 条失败。

## 3 五处分歧

### 3.1 目录快照没补 `stop`／`interrupt`（带红 3 条向量）

这两个是**契约隐式提供**的上下文原语：引擎的 `DslCatalog` 构造时会重新合成它们
（`HandlerDslContextNodes`），所以快照里刻意不写，反序列化时还会主动跳过。

我们只按快照建目录 ⇒ `{"op":"stop"}` 被判 `node-unknown`。
向量 025／026／027（choice 的三个 label 校验）都带一个 `stop` 收尾，于是三条全红，
而它们真正想测的 label 判定其实是对的——**噪音盖住了结论**。

修法：`FromSnapshot` 里从本地镜像补这两个（按名字取，已存在则跳过）。

### 3.2 循环上限缺失报了两个码

`{"op":"loop"}` 缺 `times`：我们同时报 `pin-missing` 和 `loop-unbounded`，路径都是 `actions[0].times`。
SPEC §9.1 只要后者（「不落默认值兜底」）。向量 004 要求**恰好一个**。

同一处两个码不是「多给了信息」，而是把真结论藏在噪音里——作者会先去补 `times`，
补完发现还有一条别的错误，而那条其实是同一件事的另一种说法。

修法：`IsLoopBoundPin` 的引脚缺值时跳过 `pin-missing`（这个判定本来就有，只是漏在缺值分支）。

### 3.3 `else: []` 没报 `graph-shape`

空数组与「没有 else」语义相同，却会产出两种文本（SPEC §3），所以显式空 `else` 是错误。
我们的导出侧整段省略空 `else`，所以这条只有**读进来的文档**会碰到——
而那正是校验器该管的地方：作者手写或 AI 生成的图，空 `else` 就是会写出来。

修法：`Bodies.TryGetValue("else")` 存在且为空 ⇒ `graph-shape @ …else`。

### 3.4 `schema-version` 的路径报成 `$`

契约要 `$.schemaVersion`。差一个字段名，作者就得自己翻整份文档找是哪一行不对。

### 3.5 `script` 的 `inputs`／`outputs` 根本没建模

两处都错，方向相反：

- **读**：`inputs`／`outputs` 是数组，被当成子动作读进 `Bodies`（`Body("inputs")`）——
  引脚声明丢了，而且校验器看不到「漏写」；
- **写**：导出时强行补两个空数组——把「作者漏写」静默改成「写了空的」，
  于是 `pin-missing` 永远不会响。

修法：按字段建模（`ScriptPins`，原样保留原始 JSON，我们不解释内容），
**工厂里补、导出里不补**：

```csharp
HandlerNode.Script("return;")   // 新建：预置两个空数组（替作者补上是帮忙）
```

读取别人的文档时补上就是掩盖——「缺」与「空」必须是两件事，因为契约对它们的判定不同。

## 4 顺带：前端要能解析快照

`HandlerCatalog.FromSnapshot(JsonNode)`。理由不是「方便」，而是**职责**：
前端拿到的是快照 JSON，不是 C# 的 `HandlerCatalogDto`。第一版想走「反序列化成 DTO → 复用
`FromEngine` 投影」，`BuiltInOps` 得到 null，直接 NRE——因为随包快照里没有这个字段，
而 DTO 把它声明成非空。这条已提 issue #5。

## 5 现在的状态

```
HandlerDslVectorTests
  ├─ 向量目录存在且不是空集            1 条（缺检出时给出可读原因）
  ├─ check向量_前端结论与期望一致      27 条（每条一个 Theory 用例）
  └─ 向量的码都在我们的封闭集内        1 条（防「自创码」与「契约加码没跟」）
```

断言是**逐字相等**且**恰好一个错误**，与引擎侧 `VectorTests` 同口径。
两侧都绿＝没有分歧；只有一侧绿＝分歧被藏起来了。

## 6 一条经验

> **基准只有一侧在跑，等于没有基准。**

这条测试的价值不在它今天绿了，而在它以后会红：契约改判定、我们改校验器，
任一侧动一下这里先红，而不是等作者照着错提示改了三遍才发现。

同类的东西我们还有一份——`引擎目录与本地镜像一一对应`（40 个节点逐引脚比）。
那一份是「引擎 vs 我们的镜像」，这一份是「契约 vs 我们的判定」，两份合起来才盖住
「引擎改了 / 我们改了 / 契约改了」这三种漂移。
