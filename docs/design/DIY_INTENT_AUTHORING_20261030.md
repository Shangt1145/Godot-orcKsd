# OrC：傻瓜式复杂 DIY 创作与对战

日期：2026-10-30  
状态：设计提案，尚未实施

## 目标

让不懂引擎的玩家也能创造、理解、验证复杂机制，并直接用于对战。OrC（Origin Compiler）负责把文字和原语组合编译成可靠的引擎行为。

## 核心取舍

“预制体固定编排，玩家只修改 handler”适合作为第一阶段，但不应成为最终创作边界。复杂机制可能需要新增监听、记录状态、绑定子效果和延迟执行；找不到合适预制体时，创作不应立即停下来。

玩家不用理解触发器、挂载和注销；系统应根据创作意图组合这些结构。预制体作为经过验证、可以组合的机制积木，高级作者和 agent 可以继续扩展。

## 创作流程

1. **说效果**：输入描述，或继续说“改成敌方单位”“五层后消灭它”。
2. **调效果**：把解析结果展示为可读规则，点击修改对象、数值、条件和时机。
3. **确认歧义**：只对影响行为的关键问题给出具体情境与选项，选择结果写入规则。
4. **试效果**：自动准备演示场景，逐步展示触发、状态变化和清理，并解释原因。
5. **用于对战**：发布固定版本的规则资产及依赖，单机与服务端执行同一份编译产物。

文字与原语编辑共用一份结构化规则。保留作者的手动修改；生成的 csx 是编译产物，高级脚本编辑仍可提供。

## 技术分工

| 部分 | 职责 |
|---|---|
| JS／原生解析器 | 将文字转换为统一的结构化规则，保留来源与诊断 |
| 原语编辑器 | 编辑同一份规则，展示当前能力与具体缺口 |
| 原语契约与编译器 | 检查类型、引用、作用域和生命周期，展开组合并生成 v4 资产及 handler |
| 预制体与机制积木 | 提供监听、状态、延迟、绑定、拦截和清理等可靠结构 |
| agent | 提出规则、澄清歧义、生成候选预制体及测试场景 |
| 引擎 | 校验装载并执行确定规则，决定对战结果 |

旧 JS 的解析成果优先保留，逐步解除对旧运行时的依赖。共享编译能力归引擎工具链所有，发布卡包不依赖 Godot 桥接程序集。

agent 生成内容同样接受编译、装载和行为验证。现有积木无法表达的机制明确报告缺口，允许开发扩展；不将任意文字生成脚本后直接视为实现成功。

## 首个验证场景

> 部署：选择一个友方单位。此后它每受到一次伤害，本单位获得一层记录；达到三层时，将它返回手牌，清空记录，并在下回合开始时重新部署它。

用这一张卡验证选靶、跨实体监听、状态、条件、延迟执行和清理。系统需要澄清：来源提前离场怎么办、目标返回手牌后再次打出怎么办、伤害完全抵消是否计数。

验收要求：不懂引擎的玩家能完成并修改；系统能解释关键分支；编排通过校验；单机与联机结果一致。先打通这条完整流程，再扩大原语目录。
