# OrC DIY 创作方向讨论稿

日期：2026-10-30。创作原则已确认；预制体规范、扫描生成与后端接入方式待讨论。

## 目标

Origin Compiler–KardsSimulatorDrive 的核心是原语组合、编辑与自动解析。我们的目标是让不懂代码的玩家也能制作、理解、验证复杂机制，并用于对战。

## 对「预制体固定，只编辑 handler」的看法

赞同以效果编辑器为主、卡牌作为效果容器，普通玩家主要编辑预制体开放的 handler。复杂机制可以通过多个效果组合实现，不能仅凭效果复杂，就认定必须开放底层触发器编排。

例如：

> 部署：为本单位添加一个受伤计数效果，每受伤一次增加一层记录，达到三层时执行指定行为。

可以拆成两个效果：①受伤计数效果，在受伤 handler 中维护计数、判断阈值并执行行为；②部署效果，在部署 handler 中给本单位添加前者。两者的触发结构都可以由预制体提供。状态存储需明确归属、初始化和清理规则，避免不同效果实例串用。

**需要降低的是效果拆分、选择、配置和组合的难度；是否需要新增编排结构，应由具体能力缺口证明。**

## 已确认的创作原则

1. **最后保存的版本为准。** 文字、原语或高级脚本编辑均不能仅因入口不同而取得优先权；未保存的修改不覆盖已保存版本，不在开局时重新解析文字替换规则。
2. **无法完整解析，不予解析。** 整次解析请求拒绝，不把半截效果作为成功结果写入；保留输入并说明失败位置和原因。
3. **歧义明确确认。** 只询问影响行为的问题，用具体情境让作者选择；常规默认行为可查看、可修改，选择结果写入规则。
4. **复杂编辑逐步展开。** 提供中文摘要、引用对象命名、分段阅读、复制组合、撤销重做，以及定位到具体动作的错误提示；高级参数按需展开。
5. **整理原语体系。** 区分基础原语、组合动作和旧别名；组合动作展开到共用基础语义，旧名称保留兼容映射。按表达能力、语义一致性和可用性评价，不以目录数量作为目标。
6. **采用内部测试、限制测试和公开测试。** 各阶段范围和进入条件另行确定；同时检验实际创作难度与规则正确性，不能只看编译是否通过。

## Inspector 界面大改

Inspector 需要整体重做，不能只在现有字段表单上继续增加控件。围绕效果编辑组织界面，让作者能看懂整体行为，再进入具体对象、条件、数值与动作的编辑；普通流程减少内部字段和技术概念的暴露。

大改应落实上述创作原则，保留高级入口及已有声明数据。具体页面布局和交互稿另行设计，不等待预制体规范确定后才讨论，也不预先假定扫描目录的最终形状。

## 原生与工坊如何整合

整合方向是让文字解析和原语编辑共享 handler 行为模型、原语契约与编译后端。JS 解析成果优先保留，旧运行时依赖逐步退出；Godot 负责交互，共享编译和执行能力归引擎工具链。

自动效果拆分、编排及扫描生成均未定案，不作为当前承诺。后端需提供哪些声明、扫描能生成哪些信息，待预制体规范明确后再决定。agent 可辅助制作预制体，但产物仍须验证。

## 验证方向

先用普通部署效果、条件与循环、两效果组合等代表任务验证编辑、保存和执行。自动拆分与组合的验证需等待后端能力和接入方案明确，不提前承诺自动编排。

验收重点：不懂引擎的玩家能否完成并修改；生成结构能否正确清理；结果是否符合确认后的规则；单机与服务端是否一致。暂不以原语数量或脚本编译通过率代替这些指标。
