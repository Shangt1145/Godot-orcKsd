# A.17：操作优先保留抽牌因果顺序

A.20 补充（2026-10-11）：以下 A.17 记录中的“完成入手”描述演出前置关系，现已不作为输入门槛。友方抽牌从开始飞行即创建真实可交互卡牌，鼠标按下后仅停止该牌的抽牌补间，拖拽立即接管；合法打出立即提交，使用演出排在相关抽牌之后。其他抽牌继续依次播放，未操作的受击/重排对象同样不因动画占用而被锁定。敌方回合锁保持。真实原生鼠标复现见 [STAGE_6D2_ACCEPTANCE.md](STAGE_6D2_ACCEPTANCE.md)。

## 问题

原调度将直接操作拆为高优先级主体和低优先级反馈。抽牌指令自身先显示，但其抽牌被放入普通反馈队列；下一次打牌会插在抽牌之前。若下一次使用的就是新抽到的牌，旧投影防回滚甚至会省略它的入手演出。

## 行为

- 指令、部署或攻击产生的抽牌是该操作的演出链：先操作主体，再按发生顺序逐张抽牌，然后播放后续直接操作。
- 每张牌分别完成入手并成为正常手牌；第一张完成后即可按引擎可用性操作，第二张继续演出。后续操作立即提交，演出排在抽牌链之后。
- 对独立抽牌，后续直接操作使用其卡牌或以其为目标时，先完成入手再演出该操作；只影响无关手牌的位置重排不算依赖。
- 敌方抽牌不传入卡牌身份；敌方直接操作先完成先前的隐蔽入手演出，以阵营和队列顺序判定，不猜测隐藏 UID。
- 满足前置抽牌时仍遵守反馈 FIFO 和直接操作 FIFO，不抽取队列中的晚到抽牌插到早期反馈之前。无关反馈继续让位，进行中的演出不被截断。
- 消灭退场继续可以延后；致死单位的旧画面不占用已释放槽位。敌方回合输入锁保持。

实现集中在 `PresentationPlayer`：保护直接操作内的抽牌，并逐张结算；出队前检查直接操作对等待入手卡牌的使用依赖。不修改引擎结算、卡牌效果、动画时长或输入提交机制。

## 验证

`PresentationPriorityTests` 覆盖抽牌指令后的旧牌/新牌打出、独立抽牌第二张被使用、隐蔽敌方入手、无关抽牌仍可让位、死亡反馈让位以及资源与卡牌投影不回滚。

`--verify-causal-draw` 包含真实 UI 演出和原生对局鼠标复现：打出“推进”抽两张，演出未完成时立即部署 USG 第二军；两个操作均立即提交，播放顺序为指令、抽牌、抽牌、部署，终态与引擎一致。同时确认第一张手牌在第二张抽牌开始时已可操作。

`--verify-input-scheduling` 和完整 `--verify-ui` 已包含上述检查及原有敌方回合锁、反馈优先级和非阻塞操作检查。
